# Runtime and package manifest v6

Runtime manifest v6 is the additive successor to frozen manifest v5. It adds
the complete twelve-name `AgentRuntimeCapability` vocabulary from
`agents-common/v1`, including `approvals.request` and `approvals.answer`.
`scope.sessionIds` is a closed union of a non-empty unique exact SessionId list
or one Host route-parameter binding. Package manifest v6 preserves package v5
and adds runtime manifest v6 to its closed referenced schema list.

The public TypeScript entrypoint is
`@cordisx/protocol/plugin-manifest/v6`. The machine contracts are
`plugin-manifest.v6.schema.json` and `plugin-package.v6.schema.json`.

## Exact approval route declaration

```json
{
  "name": "approvals.request",
  "required": false,
  "scope": {
    "sessionIds": {
      "kind": "host-route-param",
      "routeId": "room-session-detail",
      "param": "sessionId"
    }
  }
}
```

`routeId` is owner-local. The Host resolves it only in the authenticated
manifest owner's route registry and only while that exact route instance is
active. `param` is exactly `sessionId`; wildcards, raw paths, static broad
lists, missing values, foreign-owner routes, and name/search fallback are
invalid. Every dynamic route binding requires `required: false`, so missing
exact authority degrades the feature instead of blocking plugin activation.
Static `sessionIds` are allowed only as a non-empty unique exact list; no entry
may contain `*`. Approval capabilities must always declare one of these two
exact session scopes and cannot be unscoped.

The manifest declares maximum scope; it is not a grant. At activation/runtime,
the Host binds the immutable plugin source/id and current plugin generation,
resolves the active same-owner route instance, validates its exact non-empty
SessionId, and materializes `{ sessionIds: [exactSessionId] }` into the existing
Agent permission plan/policy/lease. The route instance and plugin generation
are lease fences. Route change/removal, generation replacement, connection
replacement, policy revocation, or unresolved/malformed parameters revoke or
deny authority. A caller cannot submit owner, generation, route, or SessionId.

`approvals.request` and `approvals.answer` remain independent capabilities.
Declaring one never grants the other. The existing `ctx.approvals` service,
Agent/Session runtime, permission ledger, prompts, decisions, audit, and
subscription lifecycle remain unchanged; v6 creates no second authority.

The frontend route `/main/chatroom/:roomId` is not an exact Session route and
cannot satisfy this binding. A plugin with that Room route must additionally
register a same-owner route such as `room-session-detail` at
`/main/chatroom/:roomId/session/:sessionId`, then reference exactly that owner-local id
and `param: "sessionId"`. The route is a normal valid `route.v2` declaration;
its `id` equals the binding `routeId`, its `path` contains the declared
`:sessionId` exactly once, and its owner is the runtime manifest owner. Other
route params such as `:roomId` grant no authority. The exact Session route can
be non-primary UI infrastructure, but it must be formally registered and
resolvable by the Host. V6 defines no
RoomId-to-SessionId conversion and no Shell-origin implicit authority.

Manifest v1-v5 and package v1-v5 bytes remain frozen. Older Hosts reject v6
rather than dropping its exact route scope or treating it as an unscoped
approval capability.
