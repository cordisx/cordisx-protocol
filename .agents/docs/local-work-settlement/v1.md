# Durable admitted work settlement v1

`LocalWorkSettlementV1` is an independent capability supplied as
`ctx.workSettlement`. Its discriminator is `cordisx.local-work-settlement/v1`.
It preserves [HTTP v4](../plugin-http/v4.md), including the frozen leased
`submitLocalWorkUsage` baseline and no-catch-up behavior. Consumers feature-detect
this service; absence keeps durable settlement unavailable. They must not fall
back to leased submission or another economic account.

## Authority and wire

`settle(binding)` accepts only origin, sourceId, instanceId and the
`local-work-income` audience. The same designated provisioned owner, enrolled
Host-profile local key, original economic account and exact loopback target used
by HTTP v4 apply. The Host obtains a signed local-wallet challenge and privately
reads its classified `WorkUsageSnapshotV2`. The caller supplies no snapshot,
amount, account, cursor, baseline, epoch, lease or history declaration. Native
identity reads are not part of settlement.

The Host signs `LocalWorkSettlementPayloadV1` with the enrolled local key using
`localWalletBytes` and its existing `cordisx.local-wallet/v1\n` domain. The
payload's distinct contract, complete binding, nonce, expiresAt, local subject
and ready snapshot are signed together. The fixed route is
`POST /v1/income/work/settle`. A server verifies all pins and consumes the nonce;
it never accepts the old observation contract at this route.

The signed response reuses `LocalWalletResultV1`. Host checks the complete
response signature, exact binding/nonce/subject and the original wallet account.
`result.receipt` must match `LocalWorkSettlementReceiptV1`: exact scope/source,
epoch, revision, admitted tokens and observation time of the submitted snapshot,
original instance/account binding, safe nonnegative amount, remainder below
10,000, partial coverage and policy `durable-admitted-v1`. The exported
`localWorkSettlementReceipt` helper checks these pins only; it neither verifies
signatures nor grants financial authority. Consumers receive an HTTP response,
not signer keys or a reusable credential.

## Persistent accounting

The economic owner keeps one persistent frontier, remainder and receipt history
for the original account and unique work scope. In the same epoch it settles
`Tnext - Tpersisted + Rpersisted`, issuing its integer quotient by 10,000 and
retaining the remainder. Reconnection, renderer disposal, temporary failure,
unknown response completion and elapsed time cannot clear this financial state.
A new epoch starts a new token frontier without cross-epoch subtraction and
retains already earned remainder. Scope/source conflicts, rollback, conflicting
revision and retired epoch reuse fail closed. Repeated or concurrent snapshots
return the same receipt identity; durable idempotency cannot depend on a mutable
server-derived baseline flag.

Initial policy adoption is a separate server transaction with verified original
ownership, unique scope binding and permanent exclusion of the old work reward
channel. A pristine first adoption may settle the signed current epoch's
Host-admitted cumulative prefix from its defined zero origin only when prior
payment evidence and conflicting issuer ownership are excluded. It must not
pretend that an empty directory proves historical absence. Existing financial,
legacy producer, pending operation or work history requires reconciliation.
Fence, initial accounting, frontier, remainder and receipt commit atomically.
Legacy leased submissions cannot reset an account with durable policy. Host
also permanently binds a work scope to its original realm and account before
signing durable settlement. Source aliases do not establish new ownership;
owner disposal and unknown completion preserve custody. Concurrent or earlier
legacy issuance attempts must exclude pristine adoption in another independent
server store. Conflicting targets require reconciliation rather than fallback.

The admitted ledger excludes first-discovered raw historical prefixes, game
work, forks/subagents and unknown sources under its documented policy. Partial
coverage is explicit. A settlement receipt proves neither complete historical
usage nor migration of unverified Pet balances. Uncovered raw/pre-ledger history
remains separately unresolved; already paid sponsor rewards cannot be minted
again. The UI must state its covered range and any unresolved history.

## Lifetime and security

Settlement shares the owning HTTP client's private principal and lifetime.
HTTP disposal, owner/generation retirement, permission loss, profile/registry
revocation or trust/key replacement fences both dispatch and late results.
Each attempt retains one 15-second transport deadline, including permission
and queue waits; this deadline is not a financial continuity lease. Server
commit with an unknown response is recovered by a later verified snapshot and
persistent receipt/frontier reconciliation, never by clearing earned state.

Signing authenticates a Host-admitted observation, not cloud billing or a
sandbox against trusted local code. Server-owned accounting, nonce validation,
unique scope ownership, permanent producer exclusion and atomic receipt storage
remain necessary even for valid signatures. There is no quota budget or caller
chosen top-up amount.
