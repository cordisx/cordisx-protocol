# Plugin HTTP v2

Experimental successor to [v1](README.md), with the same connection, request,
exchange, consent and failure types. The [types](../../../types/plugin-http.v2.d.ts)
add explicit `retain`, `resume` and `forget`. A missing v2 capability must be
reported unavailable for durable sessions; consumers must not silently create a
new remote identity after a transient restore failure. No automatic v1 upgrade
or credential migration is promised.

## Ownership and account partition

A retained session is bound to the exact Host profile, authenticated Host account,
plugin installation source and plugin ID, canonical HTTP origin, and caller
sourceId/accountId labels. The Host derives and verifies its account partition;
plugins cannot submit a native identity, nickname, display profile or guest ID as
authentication. Empty accountId is allowed as a plugin partition label, but never
removes the authenticated Host-account fence. Unknown, unavailable or signed-out
Host account sources fail closed without disclosing another account's entries.
sourceId is 1..256 characters, accountId 0..256; neither may contain control
characters. Origin follows v1 canonicalization and bearer HTTPS restrictions.

## Explicit lifecycle

`retain` preserves the existing owner-bound bearer connection in Host secure
storage, retaining only this exact partition. No token, storage reference, native
account identity or credential material crosses the public API. Storage failure
is unavailable, never a successful retention. The Host may replace a partition
only with an explicitly retained live bearer; an old grant must not delete a
newer retained value. Default authorize/exchange grants remain transient.

`resume` resolves only the exact retained partition and creates a fresh runtime
grant and descriptor. Old descriptors remain inert after generation replacement.
accepted/null means no retained entry; unavailable means account/store/Host
readiness failed and must not be treated as absence. The original remote token
is used unchanged. Remote session validity is established by the server, not by
labels or a profile: consumers validate using their ordinary session endpoint.
Remote expiry/rejection leads to explicit forget; network failures preserve the
session and require retry/reconciliation. No expired token is re-signed or
re-created as the prior remote owner.

`dispose`, generation retirement and Host shutdown abort requests, discard live
grants and remove transient secrets, preserving explicitly retained sessions.
`revoke` remains an explicit credential revocation: it removes the matching
retained revision and aborts its grants. `forget` removes the exact partition
and retires its live grants, including when called without an in-memory handle.
Consumers perform the server's ordinary logout/revoke operation and forget on
active logout; removal failure must not be reported as successful logout.
An account change makes retained grants unavailable and fences late responses.
Returning to an account may resume its still-valid original session unless
explicitly forgotten, expired or revoked remotely.

## Security analysis

This is cooperative Host credential protection within v1's trusted renderer
boundary, not a sandbox or proof of remote identity. Credentials are stored only
in a Host-controlled secure backend; unsupported platforms fail closed. No
renderer localStorage, URL, body logging or public token getter is permitted.
Persistence keys and account facts remain Host-private. Caller labels add
partitions inside an authenticated owner scope and never grant cross-owner or
cross-account authority. Implementations serialize retain/resume/forget commits
and fence owner/account changes so logout and late responses cannot revive
retired credentials. Revocation and expiry are distinct from transient failure.
