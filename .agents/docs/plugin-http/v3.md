# Plugin HTTP v3 and managed local sources v1

Experimental successor to [HTTP v2](v2.md). The [HTTP types](../../../types/plugin-http.v3.d.ts),
[signed payload types](../../../types/managed-source.v1.d.ts), [schema](../../../schemas/managed-source.v1.schema.json)
and [canonical runtime](../../../runtime/managed-source.v1.js) define separate service and wire versions.
Existing v1/v2 declarations and behavior remain frozen. Hosts without v3 must fail
closed for automatic identity and work submission; consumers must not silently create guests.

## Trust and identity

A managed binding includes canonical origin, sourceId, instanceId and audience
(`source-account` or `work-income`). This experimental version permits HTTP numeric loopback origins and HTTPS
origins for `source-account`, only after explicit Host provisioning.
`work-income` remains restricted to numeric loopback; HTTPS never grants wallet
or income authority. Older implementations reject remote bindings and must not
fall back to bearer prompts or guest sessions. HTTPS pins the exact origin and
peer keys; it does not mean every remote Host or claimed Codex subject is trusted.
Loopback addresses, configured renderer URLs, names, avatars and currentUser
display subjects are never authentication evidence. Provisioning grants the
exact owner/profile/source/audience authority. Each binding has separate Host
and server Ed25519 key pairs and pinned peer public keys; signing keys never
enter renderer code or public results.

The Host obtains the actual signed-in native account through its trusted account
adapter. The assertion subject is opaque, stable for that native account and
distinct from plugin/profile-scoped display subjects. It contains no cloud
access or refresh token. Server identity maps use pinned issuer and subject,
with their source instance, rather than displayName or caller accountId.
This proves a provisioned local Host assertion, not cloud identity attestation,
remote billing usage, or isolation against a malicious trusted Host/plugin.

## Signed wire

Canonical signing bytes are UTF-8 of `cordisx.managed-source/v1\n` followed by
JSON with recursively sorted object keys. Only plain JSON values and safe
integers are allowed, to depth32 and 1MiB. Signatures are 64-byte Ed25519,
encoded as canonical unpadded base64url. Receivers validate shape, canonical
binding, pin, expiry and nonce before acting. The [vectors](../../../conformance/managed-source.mjs)
cover serialization and key/binding separation.

`GET /v1/auth/host/challenge` accepts sourceId, instanceId and audience query
parameters and returns a signed envelope. Its payload contains the challenge
contract, binding, random32-byte nonce and Unix millisecond expiresAt within
30 seconds. The service stores the challenge and consumes each nonce once
after validating an assertion. Unknown, expired, replayed or mismatched
challenges never authorize work or sessions.

`POST /v1/auth/host/session` accepts a Host signed assertion with the same
binding, nonce and expiresAt, plus opaque subject and optional displayName.
An optional existing opaque connection can supply its source bearer only
through the Host to this exact pinned origin. The server verifies the valid
original guest session and its source/instance before any ownership upgrade;
existing different accounts conflict rather than merge. Original guest records
remain preserved if no valid previous authority is supplied.

`POST /v1/income/work` accepts a signed work observation with binding, nonce,
expiresAt, subject, Host leaseId, continuity and the actual classified
WorkUsageSnapshotV2. The public caller cannot provide tokens, amount, snapshot,
cursor, profile path or accountId. The Host reads its own current-profile work
ledger. Game, fork/subagent and unknown sources remain excluded by its policy.
The source derives its immutable account from subject and instance, and owns
durable frontier, fixed rate, remainder, deduplication and transactional receipt.

Both successful POSTs return a server signed result with the result contract,
binding, consumed request nonce, subject and result object. The Host validates
the pin and all bindings before exposing the result. Session results contain
instanceId, account.id and a sessionToken; the Host strips sessionToken and
stores the source-specific bearer securely. Issuer results contain safe wallet
identity and receipt fields, with no user or issuer bearer. No automatic POST
replay is permitted; uncertain mutations require source reconciliation.

## Lifecycle and income continuity

Managed methods use a Host-owned absolute deadline at most 15 seconds from
client invocation. It covers permission checks, bridge and authority queueing,
initial trust/native reads, signing, transport and final account/credential
checks. The Launcher must retain that deadline rather than reset it on receipt;
late delivery and late asynchronous continuations cannot sign, send, accept or
mutate a newer operation's continuity. Expired unexposed credentials retire.
The deadline is implementation metadata, never a caller-controlled amount,
usage snapshot or native identity.

An acknowledged Host result ends that operation's signing authority; it does
not prove an uncertain server mutation had no effect. `deadline-exceeded`
after the shared deadline also ends further signing authority. By contrast,
`host-unavailable` from a failed bridge/transport is unknown completion and
must not be treated as owner retirement or permission to replace an active
issuer intent. Source reconciliation and conservative baseline recovery remain
required. Owner crashes or missing terminal evidence preserve active intents.

Sign-out, native account switch, source logout, owner retirement and Host
closure invalidate applicable active grants and fence in-flight results.
Managed account labels persist privately with retained credentials; retain
cannot move a grant to another native account and resume cannot restore it
under a different account. Source bearer exchange preserves these fences.
All redirects are denied and ambient credentials are omitted.

First observation in a new owner/account generation, a new lease, unavailable
observation, failed send, explicit baseline request or a gap over15 seconds
requires baseline. Eligible owners heartbeat at most5 seconds apart. Baseline
only advances the source's frontier and forfeits historical income; it never
rewinds an existing epoch/frontier or enables duplicate issuance. The owner
requests baseline when resuming after retirement proof or usage unavailability.
The source also rejects expired leases, rollback, overlap and scope conflicts.
Retirement evidence remains an independent owner contract; a signature on
usage does not itself prove historical Pet retirement.

Provisioned issuer authority is restricted to the designated wallet owner and
exact work-income binding. The normal public usage permission remains required
for its client flow; a managed issuer provisioning grant explicitly authorizes
the Launcher ledger read/submission at that binding. It is stronger than a
general readable usage snapshot and must never be given to ordinary Game/user
principals. Revoking the issuer trust retires that provisioning authority.
Token issuance has no total, daily or per-account daily budget in this path;
safe integer validation, provenance, actual future classified usage and server
transaction/idempotency requirements remain in force.
