# HTTP v4: enrolled Host-profile local wallet

HTTP v4 adds an explicit local delegation domain to [v3](v3.md). It does not
change v3 Native-account authentication or remove any existing grant's pins.
The caller feature-detects v4. Older implementations return unsupported rather
than substituting Native authentication, display identity or another wallet.

The local authority is a persistent Host-profile key enrolled against one exact
loopback origin/source/instance and the existing canonical economic account.
Its subject is `host-local:` plus base64url SHA-256 of the enrolled Ed25519 SPKI
DER public key. It is not a Codex cloud identity, usage scope or plugin display
subject. All consumers use the same canonical wallet provider; they cannot
choose accountId, subject, profile path or key. The economic owner continues to
own the single account, balance, ledger, orders, frontier and coin arithmetic.

## Enrollment and preservation

`enrollLocalWallet({binding, connection})` requires a valid original
Native-pinned connection and fresh original-account checks. A retired connection
cannot enroll. The Host generates/persists its local key privately and obtains
a server-signed local challenge with audience `local-wallet-enrollment`. It
signs one enrollment payload using the original provisioned Host issuer. This
payload binds the original opaque Native subject, new local subject/publicKey,
exact target, nonce and expiry. The same request supplies the original account's
source bearer only inside Host transport. The server requires the original
subject and credential to resolve the same existing account before storing the
local alias. Two independent unbound proofs cannot be combined.

The server alias points to that account; enrollment cannot create a second
balance, merge accounts or copy/reset history. Existing different key, account,
realm or work-scope mappings conflict. The server signs its result with the same
target, nonce, local subject and original nativeSubject. Host activates local
authority only after that receipt passes all pins and original account fences.
Unknown completion preserves a pending enrollment; it does not authorize a
replacement key or automatic replay.

A separately documented trusted local provisioning/migration operation may
register the same alias only with explicit administrative authorization and
verifiable original ownership. Ordinary HTTP clients cannot choose accountId.
Access to plugin documents or a display subject is not ownership proof. This
alternative is never silently executed for an unbound current wallet.

## Local sessions and work

`connectLocalAccount(binding)` requires an enrolled, current profile authority.
It signs a `cordisx.local-wallet-assertion/v1` with that local key and audience
`local-wallet`; it never creates an unbound fallback account. The signed result
contains the same canonical account and a source session token. Host strips and
stores that token; public clients receive an opaque connection and safe result.
Reopening repeats this local handshake, not Native-bound v2 retain/resume.

`submitLocalWorkUsage(binding)` uses `local-work-income` and the enrolled local
key. Only the designated provisioned wallet owner may call it, with ordinary
usage permission. Host reads its own classified work ledger. Callers cannot
provide tokens, amount, snapshot, cursor or account. Server auth and work resolve
the same alias and preserve the original work-scope account mapping.

Existing actual-usage validation, game/fork/subagent exclusions, partial coverage,
nonce consumption, baseline, gap, no-catch-up, idempotency and atomic issuance
rules remain required. A signature is not Pet retirement evidence; unresolved
old producers/transactions keep issuance unavailable. No quota-based budget is
introduced and no official aggregate is substituted for classified work.

## Wire, lifecycle and security

All local payloads use canonical safe-integer JSON as in v3, but a separate
`cordisx.local-wallet/v1\n` signing domain. Challenges, enrollments, assertions,
work observations and results have distinct local contracts. Local envelopes
use the same 64-byte canonical base64url Ed25519 signature representation.
Public keys in enrollment are canonical standard-base64 Ed25519 SPKI DER.

Routes: `GET /v1/auth/host/challenge` for local audience challenges;
`POST /v1/auth/host/local-wallet/enroll` for enrollment;
`POST /v1/auth/host/session` for local sessions; `/v1/income/work` for local work.
Binding, signing key, subject and alias are checked together. A legacy issuer
cannot select an arbitrary local subject. Signer keys remain Host-private.

All client/owner/profile permissions, exact-origin pins, source instance,
key/registry generation, deadlines, revoke/dispose and late-result fences apply.
Local profile/key authority is explicitly independent of cloud login: cloud
logout/switch cannot select another local wallet or authenticate a remote source.
Local logout/revocation, profile switch/deletion and key rotation invalidate local
grants and work continuity. v3 Native grants still retire on Native change.
Missing/corrupt keys, registry or enrollment receipts fail closed; no silent
recreation, credential reuse from a retired grant or UID/display cache is allowed.

This delegation is local account authorization, not cloud billing attestation or
a sandbox against trusted renderer code/local administrators. Remote service
consumption retains its own separately granted authentication and agreements.

Local operations return `local-wallet-not-enrolled` only when no delegation exists for the profile and realm. `local-wallet-reconciliation-required` identifies prepared/submitted enrollment; `local-wallet-revoked` identifies explicit revocation. Network, key, owner and generation failures never become not-enrolled. Only not-enrolled permits consumers to start fresh original-account enrollment after verifying the immutable original account.
