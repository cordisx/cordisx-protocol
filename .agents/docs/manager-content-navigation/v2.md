# Manager Content navigation protocol v2

This specification is the additive declaration successor to frozen
`manager-content-navigation.v1`. It solves one generic information-architecture
case: a route title may name a top-level Manager destination while a tab that
targets that same route needs shorter or context-specific chrome text.

The machine schema is `schemas/manager-content-navigation.v2.schema.json`; the
TypeScript export is
`@cordisx/protocol/manager-content-navigation/v2`. The Host projection remains
the unchanged `manager-content-projection.v1` contract because its tab already
contains one resolved `text` value.

## Additive tab label

A v2 tab contains the same required stable local `id` and same-owner `route`
reference as v1. It may additionally contain one retained `LocalizedText`
`label`.

- When `label` is present, the Host resolves it through the declaration owner's
  normal localization scope and emits that result as the corresponding
  projection-v1 tab `text`. The explicit label is authoritative; the Host does
  not replace it with route metadata merely because the localized value equals
  another label or requires normal localization fallback handling.
- When `label` is absent, the Host resolves the target route title exactly as a
  v1 declaration does and emits that result as projection-v1 tab `text`.

The label is display data only. It does not change tab identity, route
identity, params, active or disabled state, ordering, selection, navigation,
authorization, history, breadcrumbs, page metadata, or mount lifecycle. The
Host must not infer any of those meanings from label text.

V2 deliberately adds no tab description. Projection v1 has no tab-description
seat, and adding one would require a separate renderer contract with defined
accessibility and layout semantics. V2 also adds no root redirect, default
child, path, URL, action, callback, DOM, selector, component, or renderer
handle.

## Compatibility and migration

`manager-content-navigation.v1.schema.json` and
`types/manager-content-navigation.v1.d.ts` are unchanged. A v1 declaration
continues to derive every tab text from its target route. V1 rejects `label` as
an unknown field; accepting it without the exact v2 `$schema` and
`schemaVersion: 2` is not migration.

A Host adds an explicit v2 declaration branch to its existing Manager content
navigation registry. It validates the exact schema/version pair, retains the
same owner/generation and route checks, and chooses the projection-v1 tab text
by the presence of `label`. A Host may store v1 and v2 declarations in one
registry, but their owner-qualified declaration ids and route identities share
one collision domain; registering the same live identity in both versions
fails rather than allowing one version to shadow the other.

An older Host keeps an unknown v2 declaration inactive with a compatibility
diagnostic. It must not reinterpret the label as a route title mutation, page
title, surface contribution, redirect, tab id, or plugin-rendered node. No
frozen surface-contribution, route, page, projection, or Manager settings
schema changes.
