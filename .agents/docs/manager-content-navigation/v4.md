# Manager Content navigation protocol v4

V4 is the additive successor to frozen navigation v3. It lets one
`manager.content` declaration select a Host-owned plugin configuration form as
its business body. It does not expose a form renderer, DOM mount, persistence
bridge, file path, or configuration writer to the plugin.

The public entrypoint is
`@cordisx/protocol/manager-content-navigation/v4`. It exports the declaration,
projection, command/result, subscription, and Host-internal source types. The
machine contracts are navigation v4, projection v3, and the
`manager-content-config-*/v1` schema family.

## Declaration and ownership

Navigation v4 preserves every v3 route, header, summary, subject, and tab field
and adds one optional body:

```ts
{
  kind: 'plugin-config-form'
  namespace: string
  defaultMaterialization?: {
    mode: 'missing-only'
    fields: readonly { path: readonly string[]; value: Scalar }[]
  }
}
```

Owner, profile, source, and generation are intentionally absent. The Host
derives them from the declaration's authenticated registration context. The
namespace must equal the declaring plugin id or one of its dotted child
namespaces. When this body exists the Host does not invoke a plugin-owned page
body callback for the route. The plugin contributes only its existing Config
schema and this data declaration; Host owns the form DOM, validation feedback,
keyboard/focus behavior, accessibility, draft state, save controls, and
persistence.

`ctx.settings` remains read-only. V4 does not add a plugin configuration write
method and the Host-internal source capability must not be installed on plugin
context.

## Reused configuration ledger

The projection embeds the existing `plugin-config-descriptor/v2`, rather than
defining another configuration store. That descriptor remains authoritative
for redacted schema/value/user fields, writable state, application mode,
revision, last-good revision, secret slots, identity, profile, and generation.
The config-form binding must exactly equal the descriptor identity, scope, and
namespace and also binds the declaration id.

Projection v3 adds `body.kind=plugin-config-form` with the exact binding,
monotonic presentation sequence, descriptor, and a redacted draft containing
`baseRevision`, dirty state, value, and closed validation state. Draft base
revision equals the descriptor's current revision. Secret paths never appear
in committed, user-layer, or draft values.

## Missing-only defaults

Default materialization exists only for first-use migration such as
`shortcutPolicy='enter'`. At most sixteen scalar fields may be declared. Each
path must be unique, non-sensitive, present in the resolved Schemastery schema,
and structurally equal that field's schema default. A missing or divergent
schema default rejects the declaration/materialization; the declaration cannot
become a second default source.

The Host issues `defaults.materialize` through the same exclusive config ledger
and writer as an ordinary plugin-config mutation. It tests presence in the raw
user layer, never the resolved value. Under the exact expected revision it
writes only absent fields in one atomic operation, preserves every present
field, validates the candidate, and applies the descriptor's normal
live/restart/staged policy. If all fields are present it returns `preserved`
without incrementing the revision. Repeated reloads therefore converge without
overwriting user edits. CAS mismatch conflicts without implicit retry.

## Draft commands and results

Every Host-issued command carries `$schema`, contract/version, `commandId`, the
exact binding, and `expectedRevision`:

- `draft.validate` applies bounded set/unset operations to the Host draft,
  validates without persistence, and never advances the configuration
  revision;
- `draft.save` adds a mutation id and passes the same operations to the
  existing config ledger; and
- `defaults.materialize` adds only a materialization id. Default values are
  resolved from the retained declaration and cannot be supplied by a renderer.

Results echo the complete command fence and use closed validated, applied,
staged, preserved, conflict, rejected, or unavailable outcomes. Save/default
writes advance the same revision and follow the existing `applies` mode.
Generation replacement, declaration replacement, owner disposal, failed
persistence/restart/rollback, non-writable configuration, and stale bindings
fail closed. A late result from an old binding cannot update the new draft.

## Subscription and lifecycle

Subscriptions are sequence-based and carry the exact binding on descriptor,
pages, snapshots, and closure. Replacement/reload/disposal emits at most one
terminal `disposed` update, closes with a generation/declaration/owner reason,
and forbids subsequent pages or commands. `closed` is a separate promise fence;
unknown schema/version or mismatched bindings are rejected rather than
normalized.

All public documents are structured-clone-safe and contain no DOM, callback,
raw path, native bridge, or arbitrary persistence authority. Navigation v1-v3,
projection v1-v2, and plugin-config v1/v2 bytes remain frozen.
